## 项目简介

MoonCast 是一个面向多人远程协作场景的浏览器端直播系统。房主可以共享屏幕画面和来源声音，成员之间可以实时语音通话；媒体数据不经过服务器中转，而是通过 WebRTC 在浏览器之间直接传输。

项目的核心价值在于验证 MoonBit 在真实前端应用中的可用性：客户端的房间状态、成员状态、连接状态机、offer/answer 协商、trickle ICE、控制消息、恢复策略和浅层树拓扑均由 MoonBit 编排；浏览器只承担 DOM、媒体采集和 WebRTC 原生能力。信令服务器仅负责房间管理和 SDP/ICE 转发，不接触音视频内容。

与常见“浏览器 API 演示”不同，MoonCast 已经补齐多人语音 mesh、屏幕共享、来源声音、动态拓扑、画质档位和连接恢复，形成一条可运行、可测试、可复现的 MoonBit + WebRTC 应用路径。

## 核心功能范围

- 支持房间创建、6 位房间码加入、成员列表和房主关闭房间。
- 通过 HTTP 长轮询实现房间事件流，完成成员加入、离开和状态广播。
- 为每对成员建立独立语音 P2P 连接，形成全连接语音 mesh。
- 支持麦克风静音、成员状态同步和共享声音开关。
- 支持房主共享屏幕视频与来源音频，并可在观众端播放。
- 支持浅层树状画面拓扑：
  - 观众不超过 3 人时，全部由房主直连。
  - 观众超过 3 人时，选择最多 3 个第一层中转节点，其余观众挂载到中转节点下。
  - 树深度固定为“房主 → 第一层观众 → 叶子观众”，降低房主上行带宽压力。
- 成员加入或离开后自动重新规划拓扑，并恢复剩余成员的画面链路。
- 支持三档画质：
  - 流畅：720p30，约 5 Mbps。
  - 清晰：1080p30，约 10 Mbps。
  - 高帧：1080p60，约 20 Mbps。
- 支持 ICE 连接恢复：
  - `failed` 状态立即重启。
  - `disconnected` 状态延迟观察，避免网络抖动误触发。
  - 单连接最多自动恢复 3 次，并提供手动重连入口。
- 支持 STUN 打洞，并主动拒绝 TURN/relay 候选，保证媒体链路保持纯 P2P。
- 提供拓扑规划 MoonBit 单元测试和信令服务器 Python 测试。
- 提供完整 README、构建脚本、启动命令和浏览器端到端演示流程。

## 技术方案

### 总体架构

```text
                    ┌────────────────┐
                    │ MoonBit 状态机 │
                    └───────┬────────┘
                            │ JS FFI / callbacks
                    ┌───────┴────────┐
                    │ 浏览器 API 桥 │
                    └───────┬────────┘
              getUserMedia / getDisplayMedia / RTCPeerConnection
                            │
      ┌─────────── P2P voice mesh ───────────┐
      │                                     │
房主浏览器 ─── stage ── 第一层观众 ─── 叶子观众
      │                                     │
      └──────────── Python 信令服务器 ───────┘
```

### MoonBit 职责

- `cmd/main/main.mbt`：客户端核心状态机，负责房间状态、成员状态、双通道连接、协商流程、ICE 缓存、控制消息、恢复策略和拓扑发布。
- `lib/topology.mbt`：浅层树拓扑规划，输出每个观众的画面来源节点。

### 浏览器桥职责

`static/bridge.js` 封装浏览器原生能力，包括：

- DOM 事件绑定与 UI 更新回调。
- `fetch` 长轮询信令。
- `getUserMedia` 麦克风采集。
- `getDisplayMedia` 屏幕和系统声音采集。
- `RTCPeerConnection` 创建、轨道添加、offer/answer 生成与 trickle ICE。
- 远端媒体流播放和连接状态回调。

### 信令服务器职责

`server.py` 使用 Python 标准库实现：

- 房间创建、加入、关闭。
- 成员事件广播。
- 定向 SDP/ICE 消息投递。
- 房间会话鉴权。
- 健康检查。

服务器不接收、不存储、不转发音视频数据。

## MoonBit 使用与创新点

- **状态机驱动**：MoonBit 负责完整客户端控制流，而不是只做简单计算模块，能真实检验语言在前端应用中的表达力。
- **双通道连接模型**：语音和画面使用独立 PeerConnection，语音异常不会引发画面重建，便于独立恢复。
- **纯 P2P 约束**：项目主动过滤 TURN/relay 候选，将“是否保持直连”作为明确产品目标，而不是隐式回退到服务器中继。
- **可测试拓扑算法**：浅层树规划在 MoonBit 中实现，并用单元测试验证小房间直连和大房间中转两种场景。
- **工程闭环**：项目包含构建脚本、单元测试、服务端测试、README 和端到端演示流程，不是一次性原型。

## 与 Syncast 的关系

[Syncast](https://github.com/KonnyakuMatcha/Syncast) 是我此前开发的直播协作项目，提供了更完整的健康恢复和拓扑调度设计。MoonCast 在同一作者的项目经验上，选取适合黑客松验证的核心能力，用 MoonBit 重新实现客户端主逻辑，并补齐语音 mesh、屏幕共享、来源声音、浅层树转发、画质调整和连接恢复。

因此，本项目属于基于本人项目的架构迁移与 MoonBit 重实现，不涉及对第三方项目的抄袭或未授权移植。

### 浏览器端到端验证

开发过程中已使用 Chromium 完成五页面冒烟测试：

- 1 位房主 + 4 位观众。
- 房主与 4 位观众之间建立 4 条语音连接。
- 前三位观众直连房主。
- 第四位观众通过第一位观众转发画面。
- 第一位观众离开后，剩余观众自动回到房主直连。
- 每位观众均收到画面与来源音频轨道。

## 演示流程

1. 构建项目：

   ```sh
   ./scripts/build.sh
   ```

2. 启动服务：

   ```sh
   python3 server.py --host 127.0.0.1 --port 8000
   ```

3. 打开 `http://127.0.0.1:8000/`。
4. 房主输入昵称，点击“创建房间”。
5. 四位观众分别输入昵称和房间码，点击“加入房间”。
6. 浏览器授权麦克风后，成员间自动建立语音 mesh。
7. 房主点击“共享屏幕和声音”，选择屏幕来源并勾选共享声音。
8. 观察观众端画面和声音；关闭一位中转观众，验证剩余成员自动重连。

## 已知限制

- STUN 打洞在对称 NAT 等网络环境下可能失败，项目不会回退 TURN。
- 系统声音共享能力依赖浏览器和操作系统支持。
- 系统混音可能包含远端语音，演示时建议使用耳机。
- 健康监控目前基于连接状态，尚未实现媒体帧计数和码率采样。
- 信令数据保存在内存中，服务重启后房间消失。

## 后续计划

1. **媒体健康采样**：使用 WebRTC stats 检测画面停滞、音频停滞和编码压力。
2. **拓扑择优**：结合 RTT、连接健康和中转节点压力动态选择第一层节点。
3. **语音恢复增强**：为语音通道增加独立媒体计数器和恢复策略。
4. **部署完善**：提供 Docker Compose、反向代理和证书自动化配置。
